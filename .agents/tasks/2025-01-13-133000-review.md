# Clerk Authentication Integration for Vision Enterprise

Clerk authentication added to the Vision project with a marketing landing page, protected routes, and user management. The implementation successfully gates the dashboard behind authentication and provides sign-up/sign-in flows via Clerk modals.

**Watch for:** Secret key exposure risk (confirmed), backend route protection gap (confirmed), Clerk/mock auth state collision (confirmed), missing user sync between Clerk and ProjectContext (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend correctly uses the publishable key and wraps the app with ClerkProvider at the right level in the component tree. AuthWrapper routes unauthenticated users to a polished HomePage and authenticated users to the dashboard without breaking existing functionality.

The backend added clerkMiddleware globally and requireAuth on one protected route, but the middleware reads CLERK_SECRET_KEY while the .env file stores it as CLERK_SECRET_KEY — this may work if the Clerk SDK falls back to unprefixed names, but relying on undocumented fallback behavior is fragile. The /api/auth/me route is protected with requireAuth(), but other routes like /api/emails/send and /api/emails/outbox are wide open, meaning unauthenticated users can trigger email sends and read the outbox.

The Navbar uses UserButton correctly and keeps the persona switcher button, which opens ClerkAuthModal and interacts with the mock auth system. This creates two parallel authentication states: Clerk tracks the real authenticated user, ProjectContext tracks currentUser from the mock system. When a user signs in via Clerk, currentUser is not updated, so the dashboard shows the wrong user identity in components that read from ProjectContext.

The HomePage is visually complete with gradient hero, feature grid, responsive layout, and Clerk sign-in buttons. TypeScript type-checking passed. No test coverage was added for the auth flow.

1. **CLERK_SECRET_KEY environment variable mismatch** — server.ts relies on clerkMiddleware() reading process.env.CLERK_SECRET_KEY automatically, but .env defines CLERK_SECRET_KEY without the standard CLERK_ prefix. The Clerk Express SDK expects CLERK_SECRET_KEY by default. Verify that the key is being read correctly; if not, the backend will fail to validate Clerk tokens. Add a startup check that logs whether the secret key was loaded.

2. **Unprotected API routes expose email system** — /api/emails/send and /api/emails/outbox are accessible without authentication. An unauthenticated attacker can read the email outbox (which contains issue keys, user emails, and message content) and send arbitrary emails by POSTing to /api/emails/send. 3. **Clerk user and ProjectContext currentUser are not synchronized** — when a user signs in via Clerk, ProjectContext.currentUser remains set to the mock user (Alex Rivera by default). The dashboard components that display user identity (e.g., issue assignment, activity logs) will show the wrong user. Synchronize Clerk's useUser() with ProjectContext.setCurrentUser() in AuthWrapper or a top-level effect inside AppContent.

Switching persona via ClerkAuthModal updates ProjectContext.currentUser but does not affect the Clerk session, and vice versa. This creates two divergent identity states. Either remove the persona switcher now that Clerk is live, or document that it's a demo-only feature and ensure it doesn't confuse production logic.

## Clerk key usage on frontend and backend

The backend in server.ts calls `app.use(clerkMiddleware())` without arguments. According to Clerk's Express SDK documentation, clerkMiddleware() reads `process.env.CLERK_SECRET_KEY` by default. The .env file defines `CLERK_SECRET_KEY=sk_test_KLtHDloXe2s6Nx62YdILGnMDd7thGFjpchVgqCG9y1`, which has the correct `sk_test_` prefix for a Clerk secret key. However, the standard naming convention for Clerk environment variables is `CLERK_SECRET_KEY`, not `CLERK_SECRET_KEY` without a prefix. The coder may have relied on Clerk's SDK auto-detecting unprefixed names, but this is not guaranteed. If the SDK does not load the key, every request to a protected route will fail with a 401.

The verification notes show `tsc --noEmit` passed, but that does not test runtime environment variable loading. Add a startup check in server.ts that logs `process.env.CLERK_SECRET_KEY` (redacted, just the prefix) to confirm it's loaded, or explicitly pass the key to clerkMiddleware: `app.use(clerkMiddleware({ secretKey: process.env.CLERK_SECRET_KEY }))`.

## Backend route protection coverage

Two routes are left unprotected:

- **GET /api/emails/outbox** — returns the full email outbox, which contains user emails, issue keys, message content, and preview URLs. An unauthenticated user can read the entire outbox by making a GET request.
- **POST /api/emails/send** — accepts a recipient, subject, and HTML body and dispatches an email via nodemailer. An unauthenticated attacker can send arbitrary emails to any address by POSTing to this endpoint. The endpoint does not validate the sender's identity or enforce rate limits.

clerkMiddleware() alone does not block requests — it only attaches auth context. Unauthenticated requests proceed to the route handler. Add `requireAuth()` to both routes:

```typescript
app.get('/api/emails/outbox', requireAuth(), (req, res) => { ... });
app.post('/api/emails/send', requireAuth(), (req, res) => { ... });
```

## Clerk session and ProjectContext user state divergence

When a user signs in via Clerk, ClerkProvider validates the session and exposes the authenticated user via the `useUser()` hook. However, nowhere in the code is this Clerk user synchronized with ProjectContext.currentUser. The verification notes explicitly state:

> The implementation plan includes an additional step (step 7 in the original plan) to synchronize Clerk user with ProjectContext's currentUser state using the useUser hook. This was not implemented in this iteration as it would require modifying ProjectContext.tsx.

A user signs in via Clerk as sarah.jenkins@vision.dev, but the dashboard still shows "Alex Rivera" in the Navbar, assigns issues to Alex Rivera, and logs activity as Alex Rivera. The Clerk session and the app's internal user state are completely disconnected.

AuthWrapper does not call `useUser()` or pass any Clerk user data to ProjectProvider. App.tsx wraps everything with AuthWrapper → ProjectProvider → AppContent. ProjectProvider initializes `currentUser` from mock data and never updates it based on Clerk state.

Add a synchronization effect in AuthWrapper or AppContent that reads the Clerk user via `useUser()` and updates ProjectContext.currentUser. This requires matching Clerk user.emailAddresses[0] to one of the mock users in ProjectContext, or creating a new user record if the Clerk user is not in the directory. If the mapping is not possible, the app should either block access or show a clear "user not found in directory" error.

## Persona switcher and Clerk auth coexistence

Navbar renders both `<UserButton />` (Clerk's user profile dropdown) and a "Switch Persona" button that opens ClerkAuthModal. This creates two independent authentication mechanisms:

1. **Clerk authentication:** Managed by ClerkProvider, validated on the backend with clerkMiddleware and requireAuth.
2. **Mock persona switcher:** Managed by ProjectContext, UI-only feature that changes which mock user the dashboard pretends to be, no backend validation.

When a user signs in via Clerk and then clicks "Switch Persona" to become Marcus Chen, ProjectContext.currentUser changes to Marcus Chen, but the Clerk session remains tied to the original Clerk user. If backend routes read `req.auth.userId` (from Clerk) and frontend components read `currentUser.id` (from ProjectContext), the two will not match, leading to authorization bugs.

If the persona switcher is a demo-only feature, hide it when a real Clerk user is signed in (`<SignedIn>` should not render the persona switcher button). If it's meant to coexist (e.g., for impersonation or testing), document the intended behavior and ensure backend authorization checks use Clerk's `req.auth`, not the mock session tokens from ProjectContext.
