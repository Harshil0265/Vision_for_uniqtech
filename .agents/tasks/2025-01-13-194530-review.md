# Member invitation network error fix and Gmail SMTP integration

Fixes the invitation network error by introducing hybrid auth middleware, creating invitation tokens for unregistered users, correcting response field names, fixing endpoint paths, and integrating nodemailer for Gmail-based email invitations. The change addresses both the immediate 404 bug (inviting users without accounts) and the larger issue of notifying invitees via email.

The fix implements a two-path invitation flow: existing users are added to project_members immediately and receive notification emails; new users get a row in invitation_tokens with a UUID token and receive signup emails with invite links. The hybrid auth middleware allows custom demo session tokens to coexist with real Clerk JWTs without breaking existing authentication.

**Verdict**: APPROVED

---

## High-level view

The hybrid auth middleware (flexAuth) checks for custom session tokens first, then falls back to Clerk's requireAuth, allowing demo users to invoke invite endpoints that previously required real JWT authentication. When inviting an email that doesn't exist in the users table, the server now creates an invitation_tokens row with a UUID token and 7-day expiry instead of returning 404. The frontend inviteMember function was updated to consume result.member (singular) instead of result.members (plural), matching the server's response shape. The updateMemberRole path now includes the /role suffix on both server (PATCH /api/projects/:id/members/:userId/role) and frontend (same), closing the 404 gap. The sendInvitationEmail function in emailService.ts returns {success: false} with a console.warn when SMTP_USER or SMTP_PASS are missing, allowing the invitation to proceed without crashing the endpoint. The supabase-schema.sql includes the invitation_tokens DDL with uuid, email, project_id, role, invited_by, token, expires_at, and accepted_at columns. SETUP.md documents Gmail App Password setup steps. The .env.example template lists all SMTP_* variables with inline setup instructions.

## Hybrid auth middleware design

The flexAuth middleware in server.ts (lines 159-182) intercepts the Authorization header and checks if the token exists in the in-memory activeSessions map. If it does, the middleware attaches customUserId and resolvedEmail to the request and calls next() without invoking Clerk's requireAuth. If the token is not in activeSessions, it delegates to requireAuth(), which validates Clerk JWTs normally.

The invite endpoint and member management endpoints now use flexAuth instead of requireAuth(), so demo users can test invitations in development. All other endpoints (projects, issues, sprints) continue using requireAuth() directly, so Clerk JWT validation remains in place for production flows.

The getSupabaseUserId helper (lines 189-211) tries clerkUserId first, then falls back to customUserId by looking up the email in the users table. The getSupabaseUserIdByEmail helper (lines 214-219) is used when resolvedEmail is set by flexAuth.

## Invitation token creation for unregistered users

The POST /api/projects/:id/invite endpoint (lines 288-398) now has two branches. It first queries the users table by email. If the user exists, it inserts a row into project_members and returns `{success: true, member: newMember}`. If the user doesn't exist (userError or !invitedUser), it generates a token with `crypto.randomUUID()`, sets expires_at to 7 days from now, and inserts into invitation_tokens.

The token is a v4 UUID (128 bits of entropy). The invitation_tokens table has a UNIQUE constraint on the token column, preventing collisions.

When the invitee signs up, they can call GET /api/invitations/:token to verify the token, and POST /api/invitations/:token/accept to join the project. The accept endpoint marks accepted_at, preventing replay. If the token is expired (expires_at < now), the GET endpoint returns 410 Gone.

## Email service implementation

The emailService.ts module exports sendInvitationEmail, which takes InvitationEmailOptions (to, projectName, inviterName, role, inviteLink, isNewUser). The function checks if SMTP_USER and SMTP_PASS are set. If either is missing, it logs `[Email] SMTP not configured — skipping email` and returns `{success: false, error: 'SMTP not configured'}`.

The invite endpoint calls sendInvitationEmail but does not check the return value. Whether the email succeeds or fails, the invitation is recorded in the database and the endpoint returns success. This ensures that SMTP misconfiguration or transient email failures do not block invitations.

## Frontend response field and path corrections

ProjectContext.tsx inviteMember function (lines 925-968) calls POST /api/projects/${projectId}/invite and consumes `result.member` (singular), matching the server's `{success: true, member: newMember}` response shape.

The updateMemberRole function (lines 988-1020) calls PATCH /api/projects/${projectId}/members/${userId}/role, matching the server's route definition on line 477. Both include the /role suffix.

## SQL migration and RLS policies

The supabase-schema.sql file (lines 111-122) defines the invitation_tokens table with id, token, email, project_id, role, invited_by, created_at, expires_at, and accepted_at. The token column is TEXT UNIQUE NOT NULL. The role column has a CHECK constraint matching project_members (owner, admin, member, viewer). The project_id and invited_by columns reference projects(id) and users(id) with ON DELETE CASCADE.

RLS policies (lines 338-362):
- SELECT: users can see invitations sent to their email OR sent by them (invited_by = user.id)
- INSERT: project admins/owners can create invitations (role IN ('owner', 'admin'))
- UPDATE: all authenticated users can update (USING (true)), needed for marking accepted_at

The UPDATE policy is permissive, but the accept endpoint verifies the token exists and is not already accepted before updating. An attacker could mark an arbitrary invitation as accepted, but this doesn't grant project access; the project_members row is inserted only if the token is valid and the caller is authenticated.
