# Project persistence, due dates, and file attachments

This change adds three features: localStorage key standardization with full Supabase persistence for projects, due date and assignment tracking for issues, and file attachment support with Supabase Storage. Projects now survive browser refresh, issues can have due dates with visual overdue indicators, and users can upload files to issues with role-based access control.

**Watch for:** **(confirmed)** localStorage fallback for attachments not implemented - base64 data URI fallback missing despite acceptance criteria requirement. **(confirmed)** Missing useEffect import causes runtime error in IssueDetailModal when accessing React.useEffect. **(confirmed)** Team members and current user localStorage keys still reference legacy 'omniplane_' prefix alongside 'vision_' fallback. **(likely)** File upload size limit validation only on backend - no client-side prevention before upload attempt. **(confirmed)** assignedAt timestamp logic has asymmetry: set on create when assignee exists, but update path only sets when transitioning from null.

**Verdict**: NEEDS_CHANGES

## High-level view

Projects are now properly persisted through both localStorage (for fallback) and Supabase API, with PUT and DELETE endpoints added to server.ts alongside the existing POST and GET. The localStorage key migration standardizes on 'vision_' prefix across most storage keys, though team members and current user keys still check the old 'omniplane_' prefix as a fallback.

Due date support adds datetime-local inputs to create and detail modals, automatic assignedAt timestamp when an issue is first assigned, visual overdue indicators (red borders) on cards, and sort-by-due-date in the backlog view. The assignedAt logic has an edge case: it sets the timestamp on create if the assignee is populated, but the update path only fires when transitioning from null to non-null.

File attachment infrastructure uses multer for multipart uploads, stores files in Supabase Storage at `{projectId}/{issueId}/{uuid}-{filename}`, tracks metadata in an attachments table, and includes role-based permissions (viewers cannot upload or delete). The attachment fetch on modal open was initially broken (fetchAttachments defined but never called) and has been fixed with a useEffect hook. Field name transformation converts snake_case database columns to camelCase for the frontend Attachment interface.

The localStorage fallback for attachments - storing as base64 data URIs with a 1MB limit - was specified in acceptance criteria but not implemented. The code assumes Supabase Storage is available.

## Project persistence and localStorage standardization

Three legacy fallbacks remain: `localStorage.getItem('vision_team_members') || localStorage.getItem('omniplane_team_members')` on line 152, same pattern for current user on line 161, and notifications on line 171. These preserve backward compatibility but violate the acceptance criterion "no 'omniplane_' keys remain". If backward compat is intentional, document it. Otherwise, remove the `|| localStorage.getItem('omniplane_...')` fallback.

## Due date and assignment timestamp

The assignedAt logic sets the timestamp when an assignee is first attached to an issue. In createIssue (ProjectContext.tsx line 583-585), if `assignee` is truthy, assignedAt is set to now. In updateIssue (line 642-647), if `updates.assignee` is truthy and `issue.assignee` is null, assignedAt is set to now.

This creates an asymmetry: if an issue is created with assignee A, then later reassigned to user B, assignedAt remains at the original timestamp. The feature spec says "set assignedAt automatically when assignee is first set", which could mean "first time any assignee is set" (current behavior) or "each time a new assignee is assigned" (not implemented). The current behavior matches the spec literally but may not match user intent if they expect to see when the current assignee was assigned.

## File attachment upload and storage

POST /api/projects/:projectId/issues/:issueId/attachments (lines 1289-1399) receives multipart/form-data via upload.single('file'). It verifies the user is not a viewer, confirms the issue belongs to the project, generates a unique file ID, uploads to Supabase Storage bucket 'issue-attachments' at path `{projectId}/{issueId}/{fileId}{extension}`, inserts metadata into the attachments table, and returns the public URL. Both GET and POST transform snake_case column names (mime_type, uploaded_at, uploaded_by) to camelCase for the frontend.

DELETE /api/projects/:projectId/issues/:issueId/attachments/:attachmentId (lines 1467-1541) checks if the user is the uploader or an admin/owner, deletes the file from storage, then removes the database row. If storage deletion fails, the operation continues to clean up the database entry (fail-forward to avoid orphaned metadata).

The fetchAttachments function (lines 112-133) was defined but never invoked on component mount. The fix adds a useEffect hook that calls fetchAttachments when selectedIssue.id changes. However, the import statement on line 1 does not include useEffect, so this will cause a runtime error.

## localStorage fallback gap

FEAT-003 acceptance criteria requires: "localStorage fallback stores attachments as base64 data URIs (1 MB limit per file in fallback mode)". The findings note: "localStorage fallback for attachments was not implemented as it requires base64 encoding which adds significant complexity and the feature spec indicates Supabase is the primary target."

This is a blocking gap. The uploadFile function in IssueDetailModal only calls the Supabase API. When !isSupabaseConfigured, uploads will fail. The acceptance criteria and step 10 of FEAT-003 both specify the fallback behavior.

To implement: in uploadFile, before constructing FormData, check `if (!isSupabaseConfigured)`. If true, use FileReader.readAsDataURL to convert file.buffer to base64, enforce 1 MB limit (1024 * 1024 bytes), construct an Attachment object with id: randomUUID(), filename: file.name, size: file.size, mimeType: file.type, url: (base64 data URI), uploadedBy: currentUser, uploadedAt: now, and append to issue.attachments array in localStorage. In the attachment list, detect data URI URLs and render them directly (img src for images, download link for others).

## Role-based access and permissions

DELETE further restricts to uploader, admin, or owner. The IssueDetailModal conditionally renders the delete button based on `userRole !== 'viewer' && (currentUser.id === att.uploadedBy.id || ['admin', 'owner'].includes(userRole))` (approximate logic from context). This matches the server-side check.

## Type safety and error handling

The multer fileFilter (lines 55-90) rejects disallowed file types before upload begins, preventing wasted bandwidth. However, the client-side accept attribute on the file input may allow files that the server rejects (e.g., if MIME type is misidentified by browser). The accept attribute should mirror the server's allowedMimeTypes and allowedExtensions.

Server endpoints check that issues belong to the specified project (lines 1333-1339 in POST, lines 1441-1447 in GET, similar in DELETE). This prevents cross-project attachment injection.
